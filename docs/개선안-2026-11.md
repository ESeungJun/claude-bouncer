# claude-bouncer 개선안

점검 기준: `b36d2ba` (v0.3.7), 2026-11-10. 저장소는 고치지 않았다. 측정은 임시 폴더 복사본에서 했다.

## 한 줄 정의

Claude Code 를 터미널 여러 개에 띄워 두고 다른 일을 하는 개발자가, 세션이 끝났거나 권한·입력을 기다릴 때 화면 위 도트 펫("클로디")이 커서 앞으로 와서 어느 프로젝트·브랜치·터미널 탭인지 카드로 알려 주는 데스크톱 앱.

## 컨셉·의도

- 목표 다섯 가지(`docs/기획서.md`): 귀엽고 같이 놀고 싶은 펫 / 누가 불렀는지 카드 한 장으로 / 일하는 중 방해되지 않게 / 비개발자도 설치 파일 하나로 / 남의 컴퓨터 설정은 건드리지 않게.
- 대상: Claude Code 를 여러 터미널·IDE 에서 동시에 돌리는 사람, claude.ai 웹 답변을 기다리는 사람.
- 핵심 가치는 "창을 오가며 확인하는 일을 없애는 것". 펫 놀이(밥·축구·미니게임·사진으로 만든 스킨)는 상주할 이유를 만드는 장치다.
- 배포: GitHub Releases. macOS 는 Developer ID 서명·공증 dmg/zip, Windows 는 NSIS. 앱 안 자동 업데이트. MIT. 수익 모델 없음.

## 지금 있는 기능

코드 기준. README 와 어긋나는 항목은 찾지 못했다.

- 훅 4종(Stop·Notification·UserPromptSubmit·SessionEnd)을 `~/.claude/settings.json` 에 넣고(`scripts/install-hook.js:52-59`), 훅 스크립트가 `127.0.0.1:17891/notify` 로 보낸다. 토큰 인증·Origin·Host 검사 있음(`lib/server.js:50-67`).
- 카드: 종류·프로젝트·브랜치·마지막 요청·요약·걸린 시간·터미널 탭. 눌러서 iTerm2/터미널 탭, tmux pane, Orca 탭, 그 밖은 앱 단위로 이동(`lib/focus.js`).
- 권한·입력 카드는 처리될 때까지 유지. macOS 에서 그 터미널로 직접 가면 자동 정리(`main.js:388-403`).
- 패널 4탭(알림함·세션·펫·설정), 트레이 카운트, 시스템 알림 옵션, 방해 금지, 집중 모드, 돌아다니기 끄기, 단축키 호출.
- 펫: 배회, 쓰다듬기, 드래그·던지기, 밥, 축구, 미니게임 2종, 배고픔·재미·기운, 레벨.
- 사진 → 도트 스킨(Higgsfield MCP 로그인 또는 API 키), 기본 스킨 3종, 제작 요청 메일.
- claude.ai 브라우저 확장(`extension/`): 답변 시작·끝 감지, 탭 복귀.
- 자동 업데이트(SHA256 검증 후 교체).

## 구조와 스택

- Electron 44, 의존성은 `@modelcontextprotocol/sdk` 하나. 번들러·프레임워크 없이 순수 JS.
- `main.js`(1111줄): 창 2개(전체 작업 영역 투명 오버레이, 패널), 트레이, IPC, 업데이트, 커서·유휴 피드.
- `lib/sessions.js`: 훅 이벤트 → 세션·알림 기록(순수 Node, 테스트 있음). `lib/server.js`: HTTP 수신. `lib/focus.js`: osascript·lsappinfo 로 터미널 전환·전면 앱 조회. `lib/store.js`: 디바운스 JSON 저장.
- `renderer/js/overlay.js`: 프레임 루프·클릭 통과. `pet.js`: 상태 기계. `notify.js`: 카드. `play.js`: 놀이. `sprites.js`: 도트 합성·캐시.
- 세션 감지는 폴링이 아니라 훅 푸시다. 로그 tail·프로세스 목록 조회는 없다. 트랜스크립트는 Stop 때만 끝 256KB 를 한 번 읽는다(`lib/sessions.js:48-82`).
- 저장: `userData/state.json`, `history-v2.json`(최근 100건), `skins.json`.

### CPU 실측 (최우선 과제)

환경: Apple M5 Pro, 모니터 3대(내장 3456×2234, 2560×1440@60, 1440×2560@60), Electron 44.7.0 비패키징 실행. 각 행은 시작 6초 뒤 10초 구간의 `ps` 누적 CPU 시간 차이, 1회 표본. 값은 코어 1개 대비 %. WindowServer 는 시스템 전체 값이라 다른 앱 영향이 섞인다.

| 조건 | main | GPU | 오버레이 렌더러 | 앱 합계 | WindowServer |
|---|---|---|---|---|---|
| 앱 없음(기준선) | – | – | – | – | 16.9 |
| 원본, 돌아다니기 켬(기본값) | 3.4 | 5.0 | 7.2 | **15.7** | 52.0 |
| 원본, 권한 카드 1장 대기 | 3.8 | 6.1 | 7.6 | **17.6** | 43.3 |
| 원본, 계속 걷게 강제 | 1.7 | 2.4 | 3.9 | 8.0 | 30.1 |
| 원본, 돌아다니기 끔(펫 정지) | 1.4 | 1.2 | 2.5 | **5.2** | 10.3 |
| 변형 A: 커서 폴링 33→250ms, 정지 | 0.4 | 1.3 | 2.5 | 4.3 | 11.0 |
| 변형 B: A + 정지 때 프레임 5fps, 정지 | 0.4 | 0.7 | 0.2 | **1.3** | 17.4 |
| 변형 C: A + 30fps 상한, 계속 걷기 | 2.1 | 1.7 | 3.1 | 7.0 | 20.8 |

메모리(RSS): main 156~190MB, GPU 73~88MB, 네트워크 41~53MB, 오버레이 93~134MB, 숨은 패널 92~122MB. 합계 약 500MB.

읽는 법:
- 아무 일도 없고 펫이 가만히 있어도 앱이 5.2% 를 쓴다. 프레임 루프를 정지 때 늦추면 1.3% 가 된다(변형 B, 실측).
- 펫이 걷는 동안은 앱 8~16% 에 더해 WindowServer 가 기준선(10~17%)보다 13~35%p 올라간다. 사용자가 느낀 "과도한 CPU"는 이 구간일 가능성이 높다. 기본 설정에서 펫은 생각할 때마다 50% 확률로 걷는다.
- 첫 두 행이 "계속 걷기 강제" 행보다 높은 이유는 확인 못 했다(측정 중 사용자의 마우스 이동, 오버레이가 놓인 모니터 차이 가능).

### 발견한 문제

🔴 없음. 보안 쪽(토큰, Origin·Host 검사, asar fuse, 탐색 차단, 폴더만 열기)은 꼼꼼하게 되어 있다.

**🟠 1. 프레임 루프가 멈추지 않는다 (유휴 CPU 의 주원인)**
- 지금 문제: `requestAnimationFrame(frame)` 이 조건 없이 매 프레임 다시 걸린다(`renderer/js/overlay.js:418-419`, `451`). 오버레이는 `backgroundThrottling: false`(`main.js:187`)라 가려지거나 다른 Space 에 있어도 줄지 않는다. 매 프레임 `pet.update`·`pet.render`·`notify.render` 가 돌고 스타일 5개를 다시 쓴다(`renderer/js/pet.js:579-587`). 펫이 정지해 있어도 렌더러 2.5%, GPU 1.2%.
- 고치는 방법: `step()` 끝에서 다음 프레임이 필요한지 판단한다. 조건(`act` 가 idle·sit·sleep, `z<=0`, `squash` 0 근처, 놀이·메뉴·펼친 카드 없음)이면 rAF 를 걸지 않고, 다음 깨울 시각(`act.dur` 남은 시간, `blinkAt`, `sayTimer`, 10초 `needTick`) 중 가장 이른 때로 `setTimeout` 하나만 건다. `onCursor`·`onNotify`·`onData`·`onAction`·마우스 이벤트가 오면 바로 깨운다.
- 나아지는 점: 정지 상태에서 렌더러·GPU 가 거의 쉰다. 노트북 배터리.
- 예상 결과: 정지 유휴 5.2% → 1.3% 안팎(변형 B 는 5fps 로 늦춘 것만으로 이 값이 나왔다. 완전히 멈추면 더 낮다).

**🟠 2. 펫이 움직이는 동안 작업 영역 전체 크기 투명 창이 매 프레임 합성된다**
- 지금 문제: 오버레이 창이 `display.workArea` 전체(`main.js:166`)이고 투명(`main.js:167-168`)이다. 펫 한 마리가 55px/s 로 걸어도 창 전체 표면이 갱신되어 WindowServer 가 투명 전체 화면 레이어를 60fps 로 다시 섞는다. 걷기 강제 측정에서 WindowServer 30.1%(기준선 10~17%). `think()` 는 50% 확률로 걷기를 고른다(`renderer/js/pet.js:493-497`).
- 고치는 방법: (a) 바로: 걷기·달리기 중 프레임을 30fps 로 제한(`frame()` 에서 `now - last < 30` 이면 건너뜀). 걷기 스프라이트가 0.15초 주기(`pet.js:270`)라 눈에 차이가 없다. 걷기 선택 확률을 0.5 → 0.25 로, 한 번 걸으면 쉬는 시간을 길게. (b) 근본: 오버레이를 펫 주변 작은 창(예: 480×360)으로 줄이고 창 자체를 옮긴다. 축구·미니게임·카드 3장처럼 넓은 면적이 필요할 때만 전체 영역으로 키운다. poketmon_idle 이 이 방식이다(`poketmon_idle/src-tauri/src/lib.rs:262-303`).
- 나아지는 점: 걷는 동안의 시스템 부하가 줄고, 전체 화면 투명 창이 다른 앱의 합성 비용을 올리는 일이 없어진다.
- 예상 결과: (a) 걷기 중 앱 8.0 → 7.0%, WindowServer 30 → 21%(변형 C 실측, 표본 1회). (b) 는 측정하지 못했다.

**🟠 3. 오래 이어지는 상태 세 가지가 전부 풀프레임 애니메이션이다**
- 지금 문제:
  - 권한 카드가 남아 있는 동안 `think()` 가 `attend({hopEvery: 2.5})` 를 끝없이 다시 고른다(`pet.js:474-477`). 2.5초마다 점프 + 카드 `needGlow` 무한(`overlay.css:176`) + 배지 `pulse` 무한(`overlay.css:122`). 카드가 펼쳐져 있으면 `notify.render()` 가 매 프레임 `offsetWidth`·`offsetHeight` 를 세 번씩 읽는다(`renderer/js/notify.js:238-240`).
  - 자리를 비워 잠든 동안(`idleSec > 240`, `pet.js:470`) 숨쉬기가 매 프레임 scale 을 바꾸고(`pet.js:298`, `582`) 2.2초마다 z 이모트를 만든다(`pet.js:294`). 사용자가 없는 시간에 계속 그린다.
  - 작업 중 세션이 있으면 `•••` 가 무한 애니메이션(`overlay.css:140`)이고 펫이 0.12초 주기 타자 포즈를 한다(`pet.js:315`).
- 고치는 방법: 권한 카드 대기는 처음 6초만 점프하고 이후 60초에 한 번으로 줄인다(자리 비움이면 멈춤). 수면 숨쉬기는 CSS `steps(4)` 3초 주기로 바꿔 초당 1~2번만 변하게 하고 JS 루프는 1번 항목대로 멈춘다. z 이모트는 8초 간격. 카드 스택 크기는 `renderCards()` 때 한 번 재서 캐시한다.
- 나아지는 점: 권한 요청을 한참 못 본 경우, 점심 자리 비움, 긴 작업 대기처럼 시간이 가장 긴 구간의 CPU 가 정지 수준으로 내려간다. 알림 방식도 덜 시끄럽다.
- 예상 결과: 이 세 상태의 CPU 가 1번 적용 후 정지 유휴 값(1~2%)에 가까워진다. 상태별 실측은 하지 못했다(권한 카드 대기 17.6% 만 측정).

**🟠 4. 메인 프로세스가 33ms 마다 커서를 읽는다**
- 지금 문제: `setInterval(..., 33)` 이 `screen.getCursorScreenPoint()` 와 `overlay.getBounds()` 를 초당 30번 부른다(`main.js:853-862`). 커서가 움직이면 IPC 를 보내고 렌더러는 그때마다 `elementFromPoint` 로 히트 검사를 한다(`overlay.js:41-52`, `270-276`). 오버레이 위에서는 DOM `mousemove` 도 같이 와서 같은 일을 두 번 한다(`overlay.js:183-185`).
- 고치는 방법: 기본 주기를 250ms 로 두고, 펫이 커서를 따라가야 할 때(접근·축구·술래잡기·간식 들기)와 커서가 최근 움직였을 때만 33ms 로 올린다. 방해 금지·수면 중에는 1초. 히트 검사는 프레임당 한 번으로 합친다.
- 나아지는 점: 메인 프로세스 상시 깨어남이 1/8 로 준다.
- 예상 결과: main 1.4 → 0.4%(변형 A 실측).

**🟡 5. 카드가 남아 있는 동안 1.5초마다 프로세스를 띄운다**
- 지금 문제: `watchFront()` 가 터미널 카드가 하나라도 있으면 1.5초마다 `lsappinfo` 를 두 번, 전면 앱이 스크립팅 허용된 iTerm2·터미널이면 `osascript` 를 한 번 더 실행한다(`main.js:388-403`, `lib/focus.js:167-190`). 완료 카드는 30분, 권한 카드는 무기한. 방해 금지나 자리 비움에도 돈다. 1회당 CPU 는 `lsappinfo` 2.8ms, `osascript` 38.5ms(실측).
- 고치는 방법: `powerMonitor` 유휴 30초 이상이면 멈추고, 전면 앱이 바뀌었을 때만 탭을 조회한다(번들 ID 가 그대로면 `osascript` 생략). 주기를 3초로.
- 나아지는 점: 권한 카드를 오래 둔 채 iTerm 을 쓰는 경우의 상시 부하 제거.
- 예상 결과: 최악(iTerm 전면) 약 3% → 0.2% 이하. 계산값이다.

**🟡 6. 숨은 패널 창이 100MB 안팎을 계속 잡는다**
- 지금 문제: 시작할 때 패널 창을 만들어 두고 닫아도 숨기기만 한다(`main.js:247-262`, `1061`). 측정 RSS 92~122MB.
- 고치는 방법: 처음 열 때 만들고, 닫힌 뒤 5분 지나면 `destroy()`. `panelPins` 가 있으면 유지.
- 나아지는 점: 상주 메모리 약 500MB → 400MB.
- 예상 결과: RSS 약 100MB 감소. 첫 열기에 0.2~0.3초 지연이 생긴다(추정).

**🟡 7. 워크트리·같은 이름 폴더가 카드에서 구분되지 않는다**
- 지금 문제: `projectName` 이 `path.basename(cwd)` 다(`lib/sessions.js:235`, `250`). 워크트리를 `repo/.worktrees/fix-a` 처럼 두면 저장소 이름이 사라지고, 서로 다른 저장소의 `app` 폴더 둘은 같은 이름으로 나온다.
- 고치는 방법: `readGitBranch` 가 이미 `.git` 파일의 `gitdir:` 를 읽는다(`sessions.js:93-97`). 거기서 주 저장소 경로를 구해 `저장소 › 워크트리` 로 표시한다.
- 나아지는 점: 여러 워크트리를 동시에 돌릴 때 카드만 보고 어디인지 안다.
- 예상 결과: 카드 제목이 `haulProject › fix-login` 형태.

**⚪ 8. 사소**
- `ext.instances` 가 줄지 않는다(`main.js:1074`). 확장 서비스 워커가 다시 뜰 때마다 새 UUID(`extension/background.js:7`). 40초 지난 항목을 지우면 된다.
- 훅 스크립트가 헤더 9개마다 `printf | tr | cut` 을 띄운다(`scripts/send-notify.sh:41`, `47-56`). 이벤트당 프로세스 약 30개. 훅이 4종뿐이라 상시 부하는 아니다. 정제를 서버 쪽(`lib/server.js:118`, 이미 300자 자름)에 맡기면 줄어든다.
- `extension/content.js:67-70`: MutationObserver(`childList` 포함)와 700ms `setInterval` 이 같은 검사를 한다. 스트리밍 중 DOM 변이마다 `querySelector` 가 돈다. 관찰 대상을 속성만으로 좁히고 인터벌에 맡긴다.
- `prefers-reduced-motion` 처리가 `renderer/` 에 없다.

## 디자인·인터랙션 제안

비평 기준은 `impeccable` 스킬의 critique 항목(제품 고유성, 인지 부하, 상태, 모션)을 참고했다. 화면은 `docs/*.png` 와 CSS 로 봤고 실행 화면은 측정 때 잠깐만 봤다.

전체 인상: Galmuri 도트 글꼴, 종이색·클레이색 팔레트, 2px 잉크 테두리와 3px 오프셋 그림자가 일관되다. 다른 제품에 그대로 옮길 수 없는 화면이라 "AI 가 만든 티"는 약하다. 아래는 그 일관성이 깨지는 곳이다.

- 이모지 아이콘: 탭(`🔔 🖥 🐾 ⚙`, `renderer/panel.html:20-23`), 메뉴(`🍪 ⚽ 🎮 🏃`, `overlay.js:95-98`), 카드 브랜치(`🌿`, `notify.js:161`)가 OS 컬러 이모지다. 도트 세계 안에 매끈한 이모지가 섞인다. `sprites.js` 의 `ITEMS` 방식으로 12×12 도트 아이콘을 만들어 바꾼다.

- 카드 왼쪽 색 띠: 종류 구분을 띠 하나에 맡긴다. 카드 머리줄 배경을 종류색으로 채우는 쪽이 도트 UI 문법(창 제목 막대)에 맞고, 3장 쌓였을 때 종류가 더 빨리 읽힌다.
- 걷는 방식: 55px/s 로 화면을 가로지르는 배회가 작업 중 시야 가장자리에서 계속 움직인다. 기본 배회 범위를 현재 위치 반경 420px(`pet.js:121`)에서 화면 하단 띠로 좁히고, 타이핑 중(`idleSec` 이 작고 커서가 멈춰 있음)에는 걷지 않게 한다.
- 조르기: 10~18분마다 다가와 메뉴를 띄운다(`pet.js:485-488`). 집중 모드를 켜야 꺼진다. 작업 중 세션이 있을 때(`data.working > 0`)는 조르지 않는 것을 기본으로 한다.
- 10~11px 글자: 카드 시간·브랜치·터미널 줄이 10px Galmuri9(`overlay.css:185`, `199`, `203`). 1440p 비레티나 모니터에서 획이 뭉친다. 최소 11px.
- 패널(어두운 갈색)과 오버레이(밝은 종이색)가 다른 세계처럼 보인다. 패널 카드 목록만이라도 오버레이 카드와 같은 종이색 카드로 맞추면 "같은 알림"이라는 게 보인다.
- `prefers-reduced-motion`: 켜져 있으면 배회·점프·글로우를 끄고 배지와 카드만 쓰는 모드를 둔다.

### CPU 실측

방법은 점검 때와 같다(`tools/idle-cpu.js`: HOME·userData 격리, 시작 6초 뒤 10초 구간 `ps` 누적 CPU, 코어 1개 대비 %). 상태마다 3회, 원본과 번갈아 측정. 값은 앱 프로세스 합계의 중앙값(최소~최대). 측정 중 사용자가 맥을 쓰고 있어(Android Studio 등) WindowServer 값은 4~50% 로 흔들려 비교에 쓰지 못했다.

| 상태 | 원본 | 고친 뒤 |
|---|---|---|
| 정지 유휴(돌아다니기 끔) | 4.8 (3.8~5.1), 첫 회차 7.6 (7.0~11.8) | **1.0 (0.6~1.7)** |
| 권한 카드 1장 대기(8초 뒤) | 7.7 (7.1~11.0), 첫 회차 10.5 | **2.9 (0.6~3.6)** |
| 계속 걷기 강제 | 13.9 (13.0~18.8) | 10.9 (10.4~12.6) |
| 작업 중 세션 1개 | 6.7 (5.7~8.9) | **1.7 (1.6~4.1)** |
| 수면 | 13.2 (7.7~14.0) | **2.6 (2.1~3.2)** |

- 프레임 수: 정지 상태 3초에 0~2회(원본은 화면 주사율대로 초당 60~120회). 걷기는 초당 30회.
- 메모리(RSS 합계): 565~570MB → 420~450MB(패널 창을 미리 만들지 않음).
- 권한 카드 대기는 카드가 펼쳐져 있는 동안 전체 창이라, 사용자가 마우스를 움직이면 그 비용이 남는다(0.6~3.6 의 폭이 그것).

### 작은 창(점검 2b)에서 알게 된 것

- 문서의 가설("전체 창이 매 프레임 합성돼 WindowServer 가 오른다")은 걷기에서는 확인되지 않았다. 30fps 걷기에서 전체 창은 앱 6.5%·WindowServer 22.5, 펫을 따라 움직이는 작은 창은 앱 10.5%·WindowServer 30.4 였다(기준선 13~14, 같은 시간대 3회씩). 창을 초당 30번 옮기는 비용이 더 크다(main +4%p).
- 대신 다른 원인이 나왔다. 화면 전체 크기 창은 무시 상태(`setIgnoreMouseEvents`)여도 그 화면의 마우스 이동을 전부 받는다. `forward: false` 로도 macOS 에서는 멈추지 않았다(실측: 5초에 117~157건). 펫이 가만히 있어도 마우스를 움직이는 5초 동안 main 5.2%·렌더러 3.6%·GPU 1.0%, 멈추면 0.2~0.6% 였다. 사용자가 느낀 "과도한 CPU"는 걷기보다 이쪽일 가능성이 높다.
- 그래서 작은 창을 넣었다. 작은 창에서는 마우스가 움직여도(커서 보고 46~49건/5초) DOM 이동 이벤트 0건, main 0.4~1.0%.
- 걷는 동안은 전체 창보다 비싸다. `CLAUDE_BOUNCER_FULL_OVERLAY=1` 로 예전 방식(전체 창)으로 띄울 수 있다.

### 검증

- `npm test`: 79개 통과, 실패 0(기존 60 + 추가 19: `test/pace.test.js` 13, sessions 4, focus 2).
- CDP 탐침(스크래치패드 `claude-bouncer-impl/`): 화면 3대 각각에서 작은 창 위치, 걷기 중 창 추적, 점프 프레임, 권한 카드 → 전체 창 → 미루기 → 작은 창, 짧은 완료는 배지만, 밥·축구 때 전체 창과 복귀.
- 실제 `~/.claude/settings.json` 해시 전후 동일. 시험 실행은 전역 단축키를 등록하지 않는다.

### 확인 못 한 것

- 실제 마우스로 펫 누르기·끌기·카드 누르기. 합성 이벤트로만 봤다(사용자가 맥을 쓰는 중이라 커서를 움직이지 않았다). 병합 전에 직접 눌러 봐야 한다.
- 패널 열기(지연 생성 뒤 첫 열기, 5분 뒤 정리).
- 창 크기를 바꿀 때 3~5프레임 동안 펫을 숨기는데, 이 깜빡임이 눈에 거슬리는지.
- Windows, 패키징된 앱.
